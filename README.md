# DocSpace — регистрация пользователей и разграничение доступа

## 1. Описание проекта

DocSpace — веб-приложение для регистрации пользователей и управления документами с использованием дискреционной модели разграничения доступа (Discretionary Access Control, DAC).

Приложение позволяет:
- регистрировать пользователей и выполнять аутентификацию;
- создавать, просматривать, изменять и удалять документы;
- предоставлять другим пользователям права доступа к документам;
- проверять разрешения перед выполнением операций с документами.

Владелец документа самостоятельно определяет, какие действия могут выполнять другие пользователи. Проверка разрешений осуществляется на стороне backend.

## 4. Запуск приложения

Для запуска необходимы Docker и Docker Compose.

Перед первым запуском необходимо создать файл конфигурации Docker из шаблона:

```powershell
Copy-Item backend/.env.docker.example backend/.env.docker
```

В корневой папке проекта выполнить:

```bash
docker compose up
```

Команда запускает PostgreSQL, backend и frontend. При первом запуске Docker автоматически собирает необходимые образы. Перед запуском backend применяются миграции базы данных.

После запуска приложение доступно по адресу:

[http://localhost:8080](http://localhost:8080)

Для остановки приложения:

```bash
docker compose down
```

Данные PostgreSQL сохраняются в Docker volume `postgres_data`.

## 5. Регистрация и аутентификация

Регистрация выполняется через интерфейс приложения. Для создания пользователя frontend отправляет запрос:

`POST /api/register`

Пример запроса:

```bash
curl -X POST http://localhost:8080/api/register \
  -H "Content-Type: application/json" \
  -d '{"login":"student01","password":"StrongPass1!"}'
```

**Требования к логину:**
- длина от 3 до 32 символов;
- латинские буквы, цифры, точка, нижнее подчёркивание и дефис.

**Требования к паролю:**
- не менее 8 символов;
- минимум одна заглавная и одна строчная буква;
- минимум одна цифра;
- минимум один специальный символ.

При успешной регистрации backend создаёт запись пользователя в PostgreSQL. Если логин уже занят, возвращается ошибка `409 Conflict`. При нарушении требований валидации возвращается `422 Unprocessable Entity`.

Для входа используется endpoint:

`POST /api/login`

```bash
curl -X POST http://localhost:8080/api/login \
  -H "Content-Type: application/json" \
  -d '{"login":"student01","password":"StrongPass1!"}'
```

После успешной аутентификации сервер возвращает JWT-токен. Он используется для выполнения защищённых запросов.

Информация о текущем пользователе:

`GET /api/me`

## 6. Дискреционная модель разграничения доступа (DAC)

В проекте реализована дискреционная модель доступа. Каждый документ имеет владельца, который может предоставлять другим зарегистрированным пользователям разрешения на выполнение операций.

Для хранения разрешений используется таблица `resource_permissions`.

Поддерживаются три вида прав:

| Право | Назначение |
|---|---|
| `can_read` | Чтение документа |
| `can_update` | Изменение документа |
| `can_delete` | Удаление документа |

Владелец документа может назначить права другому пользователю по его логину.

**Основные правила модели:**
1. Пользователь, создавший документ, становится его владельцем.
2. Владелец может выдавать другим пользователям права на чтение, изменение и удаление.
3. Пользователь может выполнять только те операции, на которые у него есть разрешение.
4. При отсутствии необходимого права backend отклоняет запрос.

Таким образом, доступ определяется владельцем ресурса и назначенными им разрешениями.

### API для работы с документами

| Метод | Endpoint | Назначение |
|---|---|---|
| POST | `/api/resources` | Создание документа |
| GET | `/api/resources` | Получение списка доступных документов |
| GET | `/api/resources/{resource_id}` | Чтение документа |
| PUT | `/api/resources/{resource_id}` | Изменение документа |
| DELETE | `/api/resources/{resource_id}` | Удаление документа |
| POST | `/api/resources/{resource_id}/permissions` | Выдача прав доступа |
| GET | `/api/resources/{resource_id}/my-permissions` | Получение информации о правах пользователя |

Для защищённых запросов используется заголовок:

```text
Authorization: Bearer <access_token>
```

## 7. Структура базы данных

В базе данных используются три основные таблицы.

**users** — сведения о зарегистрированных пользователях:
- `id` — идентификатор;
- `login` — уникальный логин;
- `password_hash` — хэш пароля;
- `created_at` — дата создания записи.

**resources** — документы пользователей:
- `id` — идентификатор документа;
- `name` — название;
- `content` — содержимое;
- `owner_id` — идентификатор владельца;
- `created_at` — дата создания.

**resource_permissions** — разрешения на работу с документами:
- `id` — идентификатор записи;
- `resource_id` — идентификатор документа;
- `user_id` — идентификатор пользователя;
- `can_read`, `can_update`, `can_delete` — соответствующие права доступа.

Связи между таблицами обеспечиваются внешними ключами.

## 8. Безопасность: что сделано

В приложении реализованы следующие меры безопасности:

- **Хэширование паролей:** используется алгоритм Argon2id. В базе данных хранится хэш, а не исходный пароль.
- **Соль:** используется механизм соли Argon2id.
- **Настраиваемые параметры хэширования:** `ARGON2_TIME_COST`, `ARGON2_MEMORY_COST` и `ARGON2_PARALLELISM` задаются через конфигурацию.
- **Защита от дублирования логинов:** уникальность логина обеспечивается ограничением базы данных.
- **Валидация:** проверяются формат логина и сложность пароля.
- **Аутентификация:** для защищённых запросов используются JWT-токены.
- **Разграничение доступа:** backend проверяет права пользователя перед выполнением операций с документами.
- **Логирование:** регистрируются успешная регистрация, попытки регистрации с занятым логином и ошибки валидации. Пароли в логах не сохраняются.

## 9. Миграции базы данных

Для управления структурой базы данных используется Alembic.

Файлы миграций находятся в каталоге `backend/migrations/`.

Применение миграций вручную:

```bash
alembic upgrade head
```

При запуске через Docker Compose миграции применяются автоматически.

## 10. Тестирование

Для проверки backend используется pytest.

Реализовано пять автоматизированных тестов:

1. Успешная регистрация пользователя.
2. Регистрация с уже существующим логином.
3. Регистрация со слабым паролем.
4. Проверка разрешённого доступа к ресурсу.
5. Проверка отказа в доступе при отсутствии необходимых прав.

Запуск тестов из корневой папки проекта:

```powershell
cd backend
python -m pytest -v ..\tests -o pythonpath=.
```

Результат успешного выполнения:

```text
5 passed
```
